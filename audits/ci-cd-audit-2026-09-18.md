# CI/CD pipeline audit — 2026-09-18

Read-only audit of `.github/workflows/*.yml` (5 workflows), the composite action `.github/actions/setup-nix/action.yml`, the scripts those workflows execute, and the GitHub-side configuration they depend on. No files in the repo were changed. Companion to `main-audit-2026-09-17.md`, which covers `hosts/main/**` runtime state and does not touch CI.

Live GitHub state was queried read-only with the owner's authenticated `gh` (REST GETs only). That removes most of the "cannot see branch protection" limitation; the one thing still unverifiable from here is the permission set of the `FLAKE_UPDATE_TOKEN` and gcp-agent PATs (only the token owner's settings page shows that).

Live state that colours several findings (all **verified** via API on 2026-09-18):

- Repository `FilipNowakowicz/nixos-config` is **public**. The owner is the only collaborator and the only contributor in history.
- Branch protection on `main`: required status checks `["merge-gate"]` with `strict: true`; `required_approving_review_count: 1`; **`enforce_admins: false`**; **`allow_force_pushes: true`**; no rulesets; no merge queue.
- Actions settings: `allowed_actions: all`, `sha_pinning_required: false`, default `GITHUB_TOKEN` permission `read`, fork-PR approval policy `first_time_contributors`.
- Six repo-level secrets (`CACHE_SIGNING_KEY`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` from 2026-05-02; `TAILSCALE_API_KEY`, `TAILSCALE_TAILNET` from 2026-05-08; `FLAKE_UPDATE_TOKEN` updated 2026-07-24). The one environment, `homeserver-gcp-deploy`, has **no** protection rules, **no** deployment-branch policy and **no** secrets.
- One self-hosted runner, `homeserver-gcp-deploy` (labels `self-hosted, Linux, X64, nixos, homeserver-gcp, homeserver-deploy`), registered at repo level, currently `offline`. The `Deploy homeserver-gcp` workflow is `disabled_manually`; its last successful run was 2026-08-04, and every push-triggered run from 08-07 to 08-16 ended `cancelled`/`failure`.
- `Tailscale ACL drift` has failed on all 42 daily runs since 2026-08-07 (58 successes before that, last on 08-06). The failing step is `Check ACL drift` → `Fetching live Tailscale policy...` → `Process completed with exit code 22` (curl `-f` on an HTTP error).
- CodeQL default setup and Dependency Graph are active (not defined in-repo).
- Weekly flake-update PRs #401, #403, #404, #407 all merged via native auto-merge (`autoMergeRequest` set) with **zero reviews**. For #407, `merge-gate` finished 20:48:51 and the merge landed 20:48:55, so auto-merge does wait for the required status.

Confidence labels: **verified** (file read, API result, upstream object inspected), **plausible** (strong inference, not directly observed), **speculative**.

## 1. High

1. **`.github/workflows/deploy-homeserver.yml:107-160`, `hosts/homeserver-gcp/github-runner.nix:7-33,56-58`, `hosts/homeserver-gcp/default.nix:74-77,281-285`** — A persistent, root-equivalent self-hosted runner is registered to a **public** repository. The runner runs as `user` (`github-runner.nix:17`), `HOME=/home/user` with `ProtectHome = false` (`:18,31-33`), and the sops-installed self-deploy key at `/home/user/.ssh/id_ed25519` (`default.nix:281-285`) is authorized for `user` itself (`github-runner.nix:56-58`); `wheelNeedsPassword = false` (`default.nix:77`). So although nixpkgs' unit sets `NoNewPrivileges = true` (nixpkgs `github-runner/service.nix:420`), any job on this runner gets root with `ssh user@127.0.0.1 sudo …` — the same trick `deploy-homeserver.yml:125-135` uses on purpose. The `if:` guard at `:64-67` protects only _this_ workflow: on `pull_request` GitHub runs the PR's own copy of `.github/workflows`, so a PR (fork or same-repo branch) can add a job with `runs-on: [self-hosted, homeserver-deploy]` and no guard. GitHub's own guidance is not to use self-hosted runners with public repos for exactly this reason. Mitigating today: the approval policy is `first_time_contributors` and nobody but the owner has ever contributed, so an outsider's workflow needs one "Approve and run" click; the runner is offline and the workflow disabled while the GCP hosts are paused; the environment (`:116`) adds nothing because it has no rules, branch policy or secrets. Disabling the workflow does **not** unregister the runner. `hosts/homeserver-gcp/CLAUDE.md:77-88` documents the root-equivalence for people who can merge to `main`, but not the "any workflow file in any PR" shape. **Verified** (repo visibility, runner, approval policy, environment via API; privilege chain by reading). This becomes the top item the day `homeserver-gcp` is un-paused. Next: while paused, delete the runner registration (`Settings → Actions → Runners`) so the label is unroutable; longer term, drop the runner model — either pull-based (a host timer that fetches `main` and switches, which also removes the "runner SIGKILLed mid-switch" and registration-GC gotchas in `CLAUDE.md:36-49,175-202`) or a GitHub-hosted job that reaches the host over an ephemeral tailnet node using secrets held in an environment restricted to `main` (`lib/hosts.nix:103` already grants `tag:ci → homeserver-gcp:22`, see Low #9). At minimum set fork-PR approval to "all external contributors" and never approve a fork run without diffing `.github/`.

2. **Branch protection (`enforce_admins: false`, `allow_force_pushes: true`) + every automation identity is the admin's own** — With "Do not allow bypassing" off, all of `main`'s rules are advisory for the owner, and every token in the pipeline acts _as the owner_: `FLAKE_UPDATE_TOKEN` (PRs authored by `FilipNowakowicz`), the gcp-agent's fine-grained PAT (`docs/security.md:145`, `hosts/gcp-agent/default.nix:279-285`), and the runner PAT. Evidence the bypass is exercised: direct pushes to `main` on 2026-08-10 (`f6182bc`), 07-25 (`bcd16fe`, `cee56ac`), 07-24 (`019590a`), 07-20, 07-17, 06-25 (×2), 06-21, and the unpushed local `1394e6d`; four bot PRs merged with 0 reviews against a 1-review rule. Because `deploy-homeserver.yml:15-28` and `tailscale-acl-drift.yml:4-11` fire on `push`, a direct or force push is a live action on the tailnet ACL and (when enabled) a root activation on the homeserver, with no `merge-gate` in front of it (the deploy workflow's own `validate` job does re-run `flake-eval`/`light`/host build, `:88-101`, so a broken push is still caught there — the ACL path has only the package build in `apply-tailscale-acl.sh:41`). `docs/security.md:479-485` states "no agent holds merge-to-main rights that bypass branch protection"; that is true only by convention (`scripts/agent-review-pr.sh:20` avoids `--admin`), because a PAT with `contents: write` acting for an admin can push straight to `main`. The 1-review rule itself is undocumented anywhere (`CLAUDE.md:76-79`, `README.md:349-355` mention only `merge-gate`) — either it is a stray setting or it is silently not doing its job. **Verified** (API + git log + PR review counts); the agent-PAT bypass mechanics are **plausible** (GitHub semantics, not exercised). Next: enable "Do not allow bypassing the above settings" and disable force pushes (the owner then always goes through a PR, which `CLAUDE.md` "Preferences" already asks for); delete the review requirement or make it real; move the agents onto a non-admin machine identity (a GitHub App installation or a second account with `write` only) so bypass is structurally impossible rather than a script convention.

## 2. Medium

1. **`.github/workflows/flake-update.yml:42-71` → `nix.yml` → `deploy-homeserver.yml:15-27`** — The weekly path grants every flake input's upstream unreviewed code execution on the fleet. `nix flake update` (`:43`) takes whatever each input's branch currently points at, `create-pull-request` + `gh pr merge --auto --squash` (`:54-71`) merge it once `merge-gate` is green (demonstrated: #407 merged 4 s after the gate), and the merge commit touches `flake.lock`, which is in the auto-deploy path filter (`deploy-homeserver.yml:26`) and is what the owner's next `sudo nixos-switch-main` builds. The only gate is "does it evaluate, build and pass the profile/smoke tests"; `cve-scan` is not required (Low #3). The inputs include code that runs as root at activation time — `deploy-rs` (`flake/deploy.nix:44-47` uses its `activate.nixos`), `sops-nix`, `impermanence`, `lanzaboote` (Secure Boot signing on `main`) — and `home-manager` tracks `master` rather than a release branch (`flake.nix` inputs). This is the documented intent (`CLAUDE.md:76`), and all inputs are reputable orgs, but the trust edge is not written down next to the R2 one in `docs/security.md:302-347`, where the same shape ("CI executes whatever is on `main`, including the flake inputs") is called out. **Verified** by reading and by run/PR timestamps. Next: narrow auto-merge to `nix flake update nixpkgs` (the one input with a real security process) and batch the rest into a manually reviewed monthly PR; or keep the weekly PR but exclude `flake.lock`-only merges from auto-deploy (route them through a required-reviewer rule on the deploy environment); record the accepted edge in `docs/security.md`.

2. **`.github/workflows/nix.yml:80-96,523-561`, `scripts/ci-plan.sh:16,19,183-188`** — `merge-gate` is gated by a planner the PR itself supplies. The `changes` job runs `scripts/ci-plan.sh`, `test-ci-plan.sh`, `check-cache-config.sh` and `check-ci-build-safeguards.sh` from the PR head checkout, and `merge-gate` then requires _exactly_ what that planner planned (`require_when_planned`, `:523-533`). A PR that edits `ci-plan.sh` decides its own gate. `.agents/governance.yaml:26-44` marks `.github/workflows/`, `secrets/`, `.sops.yaml`, agent scripts and `.age` as human-review paths but not `scripts/ci-plan.sh`, `scripts/validate.sh`, `scripts/push-to-r2.sh`, `.github/actions/**`, `lib/acl.nix` or `lib/hosts.nix`, so an agent PR touching the planner plus a Nix change is `risk=low` and eligible for autonomous auto-merge; the "trusted base" property in `docs/security.md:491-493` covers only the agent gate, not `merge-gate` (the archived lesson `.agents/learning/candidates/archive/2026-06-14-merge-gate-must-run-from-trusted-base-and-bind-evidence.yml` describes this exact shape for the agent gate). Concrete existing gap, no malice required: `home/files/agents/global-development.md` is a Nix input (`home/profiles/python-development.nix:3-4`, `flake/checks.nix:67-74`) but `docs_change` (`ci-plan.sh:16`, `.*\.md$`) classifies it docs-only, so a PR changing it runs lint only (`:183-188`) although every host's Home Manager closure and a flake check change. **Verified** by reading. Next: evaluate the planner from the base ref (`git show "$BASE_SHA:scripts/ci-plan.sh" | bash`, with `test-ci-plan.sh` likewise), or make `merge-gate` require `eval` + `checks-light` unconditionally; tighten `docs_change` to `^(README\.md|docs/|[^/]+\.md|.*/CLAUDE\.md)$` so `home/files/**` never counts as docs; add the planner/validate/push scripts, `.github/actions/`, `lib/acl.nix`, `lib/hosts.nix` to governance's high-risk list.

3. **`.github/workflows/tailscale-acl-drift.yml:37,44`** — `TAILSCALE_API_KEY` expired on schedule and nobody noticed. The comment says "created 2026-05-08, expires ~2026-08-06. Rotate before then"; the secret's last update is 2026-05-08; the daily check has failed every day since 2026-08-07 with curl exit 22 on the policy GET (`check-tailscale-acl-drift.sh:22-27`). Consequences: six weeks without drift detection; any `lib/acl.nix`/`lib/hosts.nix` change pushed since 08-06 silently did not apply (`apply-tailscale-acl.sh:98-100` fails the same way); 42 red runs in the Actions tab with no escalation (GitHub's failed-run email is the only alarm, and it has clearly been tuned out). The key also carries ACL **write** scope (`apply-tailscale-acl.sh:14`) as a repo-level secret. **Verified** (run history, log, secret timestamps). Next: mint a new key, then split it — a read-only key for the scheduled check and a write key held in an environment restricted to `main` (see #4); put the expiry in a place that fires (calendar or a workflow step that fails N days before the recorded expiry); treat "same workflow red > 3 days" as an alert, not noise.

4. **Secret placement — six repo-level secrets, an empty environment** — `deploy-homeserver.yml:116` names `environment: homeserver-gcp-deploy`, but that environment has no rules, no branch policy and no secrets, so the reference is decorative. Everything sensitive is repo-level: R2 write keys and the Nix signing key that `main`/`mac` trust (`docs/security.md:302-325`), the Tailscale ACL write key, and the flake-update PAT. The `push`-to-`main` guards on the pushing steps (`nix.yml:136,223,265,279-283,351`) live inside the file a same-repo PR can edit, and on `pull_request` from a same-repo branch secrets _are_ available. Today the only identity with the fine-grained `workflows` permission needed to push a workflow edit is the owner (the gcp-agent PAT is documented as contents/PRs/issues only, `docs/security.md:145` — **plausible**, cannot verify the token), so exploitation currently needs the owner's own credential; the design still relies on that rather than on GitHub's isolation. **Verified** (secret/environment listing; workflow guards by reading). Next: create environments with deployment-branch policy `main` (e.g. `r2-cache`, `tailnet-acl`, `flake-update`) and move the write secrets into them; PR runs then cannot reach them even with a rewritten workflow, and `environment:` on the deploy job starts meaning something.

The pin is still immutable (a tag object embeds its target hash), but it is opaque to Dependabot/audit tooling and would break silently if upstream ever pruned unreachable objects. The other seven pins resolve to tagged commits: checkout `v4.3.1`/`v5.0.1`, github-script `v7.1.0`, cache-nix-action `v7.0.2`, create-pull-request `v6.1.0` (v7/v8 exist), upload-artifact `v4.6.2`, cache `v4.3.0`. There is no `.github/dependabot.yml`, and the repo-level "require SHA pinning" setting is off, so pinning is convention only. **Verified** (object fetched and inspected; API). Next: re-pin to commit `13d8dd58da0234aa297dedd986986ccb8e7f3e24`, turn on `sha_pinning_required`, and add a `github-actions` Dependabot config (its PRs go through `merge-gate` like any other).

2. **`.github/workflows/flake-update.yml:22-25`** — The job grants `GITHUB_TOKEN` `contents: write`, `pull-requests: write`, `actions: write`, but every write is done with the PAT (`:58,69`); `create-pull-request` uses the supplied token for push and API. `actions: write` in particular lets the job cancel/re-run other workflows for no reason. **Verified.** Next: reduce the job block to `contents: read` (the top-level block at `:9-10` already says so).

3. **`.github/workflows/cve-scan.yml:39-53` vs `docs/operations.md:364-367,372-377`** — The scan does fail on advisories (`exit 1` at `:50-53`), but it is a separate workflow that `nix.yml`'s `merge-gate` never `needs`, and branch protection requires only `merge-gate`. A red `cve-scan` therefore does not block the weekly auto-merge — it is a signal, not a gate. The docs call it "strictly superior, gating" and "fails its `cve-scan` gate". History: #404's PR scan failed on 09-04 and was green again on 09-10 before merge, so there is no counterexample yet, only the structural gap. The choice looks deliberate (vulnix false-positive churn, `docs/operations.md:387-389`). **Verified.** Next: pick one — add `cve-scan` to the required contexts and live with the noise, or reword the docs to "advisory signal" and keep the schedule.

4. **`.github/workflows/nix.yml:197-198`** — `nix run nixpkgs#actionlint` resolves `nixpkgs` through the GitHub runner's default flake registry (nixpkgs-unstable HEAD at run time), so the lint job's tool is unpinned and non-reproducible; `cve-scan.yml:47` does it right with `--inputs-from .`. Hosts are unaffected (`flake/hosts.nix:95-97` pins the registry, enforced by `flake/checks.nix:22-34`), so the runner-side `nix shell nixpkgs#deploy-rs` (`deploy-homeserver.yml:140`) uses the locked nixpkgs. **Verified.** Next: `nix run --inputs-from . nixpkgs#actionlint`.

5. **`.github/workflows/nix.yml:23-61` (push-policy)** — For any push whose commit is associated with a PR (i.e. every merge), `should_run=false`, so `changes` and all build jobs are skipped and `merge-gate` exits 0 (run `34522918270` for the #404 merge: every job `skipped`). The R2 publish steps run only on `push` to `main` (`:136,223,265,279-283,351`), so the signed cache and the "warm closure-diff base" step (`:275-293`) are fed **only by direct pushes** — the path High #2 wants to close. `README.md:354-355` ("only publishes on protected `main`") is therefore mostly inert, and `main`/`mac` substitute from a cache last refreshed by whichever direct push happened most recently. Not a security hole (PR builds are never published), but the cache design and the skip contradict each other. **Verified.** Next: either drop the skip (accept one duplicate build per merge) or publish from a `workflow_run`/`merge_group` job that re-uses the PR's store paths; once direct pushes are blocked, the current code publishes nothing.

6. **`hosts/homeserver-gcp/github-runner.nix:11`, `docs/operations.md:226-230`, `hosts/homeserver-gcp/CLAUDE.md:175-202`** — The runner registers with a fine-grained PAT holding repository `Administration: read/write`, the strongest repo permission (it can rewrite the branch protection that High #2 depends on, manage runners, collaborators and deploy keys). ## Checked and fine

- No workflow uses `pull_request_target`, `workflow_run`, `issue_comment` or any other trigger that runs fork code with secrets; fork PRs get a read-only token and no secrets by GitHub's rules. `deploy-homeserver.yml:63-67` additionally pins `github.repository` and `refs/heads/main`.
- Every `uses:` (8 distinct) is a full-length SHA with a version comment; seven resolve to the tagged commit upstream (Low #1 covers the eighth). `actionlint` runs on every lint pass (`nix.yml:197-198`, `.github/actionlint.yaml` declares the self-hosted labels).
- All five workflows declare a top-level `permissions:` block (`contents: read`, plus `pull-requests: read` for `nix.yml`); job-level escalations are explicit (`closure-diff-comment` `issues: write`, `flake-update` — see Low #2). The repo default is `read` and `can_approve_pull_request_reviews: false`.
- `merge-gate` is the sole required context, `strict: true` forces the branch to be current before merge, and native auto-merge demonstrably waited for it. The gate fails when any planned job is not `success` **and** when an unplanned job ran (`nix.yml:523-533`); the only `continue-on-error: true` steps are the non-blocking R2 publishes; `fail-fast: false` on the matrices cannot hide a failed leg.
- `scripts/push-to-r2.sh:40-90` allowlists derivation names from the flake's own `checks`/`packages`/`ciTests`/host toplevels, refuses non-`/nix/store` and unknown paths, and reads the signing key from a `mktemp` file that is removed on exit; `scripts/check-cache-config.sh` keeps the CI trusted key and URL identical to `lib/binary-cache.nix`.
- GHA cache keys (`setup-nix/action.yml:76-77,115-117`) derive from `flake.lock`/`**/*.nix` hashes plus fixed job suffixes — nothing attacker-influenceable — and GitHub's cache scoping means a PR cannot write a cache that `main` or another PR restores. The `nix.yml` concurrency group is keyed on PR number/ref (`:15-17`).
- Secrets and PR-derived values reach shell only through `env:` (`nix.yml:86,129-143,257-262,343-348,407-409`), never inline `${{ }}` inside `run:`; the composite action's inline `${{ inputs.* }}` values are workflow-controlled.
- `cve-scan.yml:47` pins vulnix's nixpkgs with `--inputs-from .`, and the only artifact uploaded anywhere is its text report (`:55-61`).
- No GCP credential of any kind exists in GitHub — no Workload Identity, no service-account key; `infra/*.tf` and `scripts/deploy-gcp.sh` run from the owner's workstation with local `gcloud` auth. The self-hosted-runner design removed the need for one, at the cost described in High #1.
- Hosts pin `nix.registry.nixpkgs` to the flake input (`flake/hosts.nix:95-97`, invariant `flake/checks.nix:22-34`), so the runner-side `nix shell nixpkgs#deploy-rs` uses the locked nixpkgs. `flake/deploy.nix:40-43` keeps `magicRollback`/`autoRollback` on for the auto-deploy path.
- `scripts/check-ci-build-safeguards.sh` and `scripts/test-ci-plan.sh` run on every PR (`nix.yml:89-96`) and would catch a heavy job losing its timeout/disk-reclaim steps or the planner regressing on the documented cases.
- CodeQL default setup and Dependency Graph are enabled at the repo level.

Suggested triage order: High #2 (branch-protection toggles — two clicks, no code), Medium #3 (rotate the Tailscale key, it is dead today), High #1 (unregister the runner while paused; decide the deploy model before un-pausing), Medium #4 (environments), Medium #2 (planner from base ref + `docs_change` fix), then Medium #1 as a design decision, and the Low list with the doc sweep.
